# 난지 한강공원 시간별 주차 예측 보고서

이 문서는 [nanji_ML.ipynb](/Users/electrozone/Documents/nanji_work/hmw/Note/nanji_ML.ipynb)의 흐름을 그대로 따라가면서, 데이터 이해부터 전처리, 모델 비교, 최종 해석까지 한 번에 읽을 수 있도록 정리한 보고서입니다.

## 1. 데이터 소스와 분석 목적

- 분석 대상: `estimated_active_cars`
- 의미: 특정 시각에 주차장 안에 머물고 있다고 추정되는 차량 수
- 목표: 난지 한강공원의 시간대별 주차 수요를 예측하고, 나중에 `여유 주차공간 수`로 바꿔 해석할 수 있게 정리

이번 작업은 기존 노트의 큰 흐름을 유지하면서, 전처리 단계에 아래 내용을 추가한 것이 핵심입니다.

- 입력 변수 분포 점검
- 추가 변환이 필요한지 확인
- 타깃 이상값/특이값 점검
- 머신러닝 입력 변수별 이상값 점검
- 이상값 제거 후 모델 성능 재평가

## 2. 현재 시간별 데이터가 운영시간 조건에 맞는지 확인

질문에서 제시한 운영시간 조건은 `06:00~23:00`입니다. 현재 시간별 데이터는 `00:00~23:00` 전체 행을 갖고 있지만, `00~05시`의 `estimated_entries`, `estimated_active_cars`는 모두 `0`으로 들어 있습니다.

즉 현재 데이터는 다음처럼 보는 것이 자연스럽습니다.

- `06~23시`: 실제 운영시간으로 보고 예측 대상에 포함
- `00~05시`: 운영시간 외 구간으로 보고 값은 `0`으로 유지

이번 모델에서도 같은 기준을 유지했습니다. `hour_weight`는 `06~23시`로만 계산했고, 운영시간 외 구간의 최종 예측값도 `0`으로 고정했습니다.

## 3. 시간별 데이터 생성 방식 정리

현재 워크스페이스에는 난지의 직접 실측 시간별 주차 로그가 보이지 않았고, 대신 이미 만들어진 시간별 통합 데이터셋을 사용합니다.

핵심 구조는 다음과 같습니다.

1. 난지 일별 주차 원본을 가져온다.
2. 날짜별 `주차대수`, `이용시간`을 합친다.
3. 하루 24시간으로 확장한다.
4. 평일/주말과 계절 패턴을 이용해 `estimated_entries`를 만든다.
5. 평균 체류시간을 반영해 `estimated_active_cars`를 만든다.
6. 날씨, 버스, 지하철, 자전거, 행사, 주변 인프라 정보를 붙인다.

즉 이번 모델의 타깃은 실측 시간 로그가 아니라, 일별 원본을 바탕으로 만든 시간대별 추정 점유량입니다.

## 4-1. 모델링에 쓰는 계산 규칙

이번 노트는 난지 한 곳만 대상으로 하므로, 이전 통합 분석의 핵심 구조만 가져와 단순하게 사용했습니다.

이번 모델은 한 번에 모든 것을 맞추는 방식이 아니라, **기본 흐름을 먼저 회귀식으로 잡고, 그 다음 가중치로 보정하고, 마지막에 Ridge 회귀로 남은 차이를 설명하는 구조**입니다.

왜 이렇게 나누는가:

- 난지 주차 수요는 하루 안에서 반복되는 시간대 패턴이 큼
- 같은 시간대라도 월과 계절에 따라 전체 수준이 달라짐
- 날씨, 교통, 행사 같은 외부 변수는 이 기본 흐름 위에서 추가 차이를 만듦
- 따라서 `기본 패턴 -> 월/시간 보정 -> 외부 변수 보정` 순서로 보는 편이 더 해석하기 쉽고 안정적임

기본 흐름은 아래와 같습니다.

1. `day_type x hour` 평균으로 시간대 기본 패턴을 만든다.
2. 이를 부드러운 회귀식 형태로 정리해 `base_value`를 만든다.
3. 실제값 대비 월별 차이를 이용해 `month_weight`를 만든다.
4. 운영시간 구간에서 시간대 차이를 반영하는 `hour_weight`를 만든다.
5. `pattern_prior`, `corrected_pattern_prior`를 만든다.
6. 이 값과 외부 변수를 함께 사용해 Ridge 회귀 모델을 학습한다.

각 요소의 역할은 아래처럼 볼 수 있습니다.

- 회귀식: 평일인지 휴일인지, 그리고 몇 시인지에 따라 보통 어느 정도 수요가 나오는지 보여주는 기본선
- `month_weight`: 월별로 전체 수요 수준이 높아지거나 낮아지는 부분을 보정
- `hour_weight`: 운영시간 안에서 특정 시간대가 유난히 붐비거나 덜 붐비는 부분을 보정
- Ridge 회귀: 위 패턴 정보와 외부 변수를 함께 보고 최종 오차를 줄이는 역할

누수를 막기 위해 `month_weight`, `hour_weight`는 모두 `train`만 보고 계산했습니다.

## 5-2. 타깃 값의 이상값/특이값 점검

타깃인 `estimated_active_cars`에 대해 boxplot과 IQR 기준으로 먼저 후보를 찾고, 그다음 `이상값`과 `특이값`을 구분했습니다.

### 판정 규칙

1. `Q3 + 1.5 * IQR`을 넘는 값을 1차 후보로 잡는다.
2. 후보를 작은 값부터 정렬한다.
3. 첫 후보는 `일반 구간 최대값`과 비교한다.
4. 어떤 후보가 `특이값`으로 유지되면, 다음 후보는 `직전 특이값`과 비교한다.
5. 현재 기준점과의 차이가 `IQR`보다 크면 `이상값`, 아니면 `특이값`으로 본다.
6. `이상값`만 제거하고, `특이값`은 설명만 남기고 유지한다.

이번 타깃 점검 결과는 아래와 같습니다.

| estimated_active_cars | 0.0256 | 118.8472 | 118.8216 | 297.0796 | 296.9827 | 1733 | 1733 | 0 |

해석:

- 상한선을 넘은 값은 있었지만, 이번 규칙에서는 모두 연속적인 높은 수요 흐름으로 판단됐습니다.
- 따라서 타깃에서는 제거된 행이 없었습니다.
- 노트북에는 이 과정을 설명하는 boxplot과 요약 표를 함께 넣었습니다.

## 6. 시간대 기본 패턴과 보정값 만들기

난지 한 곳만 대상으로 기본 패턴을 만들고, 계절과 시간대 보정값을 추가했습니다. 여기서는 숫자를 단순히 맞추기보다, **주차 수요가 어떤 규칙으로 움직이는지 먼저 구조를 만든다**는 관점이 중요합니다.

전체 순서는 아래와 같습니다.

1. `train(2022~2023)` 구간에서 `평일/휴일 x 시간` 평균 패턴을 학습합니다.
2. 이 패턴을 부드러운 회귀식 형태로 정리해 `base_value`를 만듭니다.
3. 기본 패턴 대비 월별 차이로 `month_weight`를 계산합니다.
4. `pattern_prior = base_value * month_weight`를 만듭니다.
5. 운영시간(`06~23시`) 안에서 시간대 차이로 `hour_weight`를 계산합니다.
6. `23시`는 흔들림이 커서 `22시` 쪽으로 조금 보정합니다.
7. `corrected_pattern_prior = pattern_prior * hour_weight`를 만듭니다.
8. 이 값을 최종 모델의 핵심 입력값으로 사용합니다.

쉽게 말하면 아래와 같습니다.

- `base_value`: 평일/휴일과 시간대만 보고도 보이는 기본적인 수요 모양
- `month_weight`: 같은 시간대라도 계절과 월에 따라 전체 수준이 달라지는 부분
- `hour_weight`: 같은 월 안에서도 특정 시간대가 더 높거나 낮은 부분

즉 최종적으로는 `기본 모양 x 월 보정 x 시간 보정`으로 큰 흐름을 먼저 만든 뒤, 그 위에 머신러닝이 세부 차이를 보정합니다.

이 방식을 쓰는 장점은 다음과 같습니다.

- 시간대 수요의 큰 흐름을 사람이 읽기 쉬운 형태로 남길 수 있음
- 월별 변화와 시간대 변화를 따로 해석할 수 있음
- Ridge 모델이 처음부터 모든 변동을 혼자 설명하지 않아도 되어 더 안정적임

## 7. 머신러닝 모델 학습과 검증

이상값 점검과 정리를 마친 뒤, 같은 구조로 다시 학습하고 성능을 비교했습니다.

실제 학습 방식은 아래처럼 이해하면 됩니다.

1. 먼저 회귀식과 가중치로 주차 수요의 큰 흐름을 만듭니다.
2. 그 결과를 `pattern_prior`, `corrected_pattern_prior` 같은 변수로 만듭니다.
3. 나머지 feature들도 함께 표준화합니다.
4. Ridge 회귀가 각 변수의 계수를 학습해 최종 예측값을 만듭니다.

즉 이 모델은 완전히 블랙박스처럼 동작하는 것이 아니라, **사람이 이해할 수 있는 패턴 정보를 먼저 넣고, 그 위에서 회귀가 세부 오차를 줄이는 방식**입니다.

비교한 두 모델의 차이는 아래와 같습니다.

- `weighted_core`: 패턴 정보 중심으로 어느 정도 설명되는지 확인하는 모델
- `weighted_extended`: 여기에 공휴일, 교통, 자전거, 행사, 날씨 정보를 더해 패턴으로 설명되지 않는 차이를 더 줄여보는 모델

Ridge 회귀를 쓴 이유도 분명합니다.

- 입력 변수가 많고 서로 비슷한 변수도 있어 계수가 쉽게 흔들릴 수 있음
- Ridge는 계수를 너무 크게 키우지 않도록 눌러 주어 예측을 안정적으로 만듦
- 가중치 기반 변수와 외부 변수를 함께 넣을 때 과적합을 줄이는 데 도움이 됨

| model_name | alpha | split | rmse | mae | r2 |
|:--|--:|:--|--:|--:|--:|
| weighted_core | 1000 | train | 53.0572 | 27.4909 | 0.7835 |
| weighted_extended | 1000 | train | 50.2907 | 26.0292 | 0.8055 |
| weighted_core | 1000 | valid | 54.2206 | 28.7543 | 0.7442 |
| weighted_extended | 1000 | valid | 50.3496 | 28.3570 | 0.7794 |
| weighted_core | 1000 | test | 59.6065 | 30.0520 | 0.7254 |
| weighted_extended | 1000 | test | 56.5583 | 28.0493 | 0.7527 |

`test` 기준으로는 `weighted_extended`가 더 좋았습니다.

## 7-1. 참고 비교: 날씨 정보만 추가한 모델

보조 비교용으로 날씨 중심 모델도 다시 평가했습니다.

## 9. 전체 결과 정리

이번 정리를 한 문장씩 요약하면 아래와 같습니다.

- 난지 시간별 데이터는 직접 실측 로그가 아니라, 일별 원본을 시간 단위로 확장해 만든 추정형 데이터셋이다.
- 운영시간은 `06~23시`로 보고, `00~05시`는 `0`으로 유지했다.
- 입력 변수 분포를 먼저 점검한 뒤, 추가 변환이 꼭 필요한지 확인했다.
- 타깃 `estimated_active_cars`에서는 상한선을 넘는 값이 있었지만 모두 특이값으로 유지돼 제거된 행은 없었다.
- 입력 변수 점검에서는 자전거 이용시간 합계, 이동거리 합계에서만 실제 제거가 필요한 값이 나왔고, 총 `8개` 행을 제거했다.
- 모델 구조는 `기본 회귀식 + month_weight + hour_weight + Ridge` 조합이며, 큰 흐름을 먼저 설명한 뒤 남는 차이를 머신러닝이 보정하는 방식이다.
- 그 후 다시 학습한 결과 `test` 기준으로는 `weighted_extended`가 `weighted_core`보다 성능이 좋았다.
- 다만 미래 시점 예측에 바로 쓰는 운영 모델로는, 외부 변수를 덜 요구하는 `weighted_core`가 더 현실적일 수 있다.

## 10. 여유 주차공간 수로 바꾸는 방법

현재 모델이 직접 예측하는 값은 `estimated_active_cars`입니다. 이 값을 여유 주차공간 수로 바꾸려면 난지 주차장의 실제 총 주차면 수가 추가로 필요합니다.

계산식은 단순합니다.

- `predicted_occupied_cars = predicted_estimated_active_cars`
- `available_spaces = max(total_capacity - predicted_occupied_cars, 0)`

예를 들어 총 주차면이 `800`이고 특정 시점의 예측 점유 차량 수가 `620`이면:

- 여유 주차공간 수 = `180`
- 점유율 = `77.5%`

즉 현재 모델은 여유 주차공간 수를 직접 예측하는 모델이라기보다, 그 값으로 바꿔 해석할 수 있는 `추정 점유량 모델`이라고 보는 것이 맞습니다.
